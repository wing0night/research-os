# Daily Journal

把日记当作个人系统的情景记忆入口：先保存当时发生了什么，再进行周期性压缩和归档。不要把一次情绪、猜测或偶然事件直接写成稳定人格。

## 存储位置

- 原始日记：`diary/entries/YYYY/YYYY-MM-DD.md`
- 总结归档：`diary/summaries/YYYY/YYYY-MM-DD-<period>.md`
- 当前状态：必要时更新 `now/README.md`
- 项目行动：必要时更新对应的 `projects/*.md`
- 长期记忆候选：先写入总结；只有稳定、反复出现或用户明确确认时，才更新 `self/`
- 临时但有价值的想法：`inbox/`

如果日期或周期不明确，使用当前日期，并在文件中注明“日期由系统推定”；不要伪造用户没有提供的时间。

## 模式一：记录日记

当用户讲述一天、一个片段、一个想法或个人信息时：

1. 判断目标日期；已有当天文件就追加，不覆盖已有内容。
2. 尽量保留用户原话，轻微整理段落即可。
3. 将内容标为事实、感受、想法、决定、任务或待确认，不替用户做心理诊断。
4. 若用户没有要求总结，不主动把内容推广到 `self/`、`now/` 或项目文件。
5. 日记末尾保留“未处理线索”，供下次总结时归档。

## 模式二：总结并归档

当用户说“总结”“归档”“回顾本周/本月”时：

1. 确定时间范围，并读取该范围内尚未总结的原始日记；同时读取相关的 `now/`、`projects/` 和最近周报。
2. 生成一份总结归档，不修改原始日记。总结至少包含：
   - 时间范围与来源文件
   - 发生了什么：只写可追溯事实
   - 感受与能量：保留主观体验，不当作医学结论
   - 反复出现的模式：标注为观察或推测
   - 当前项目进展：目标、输入、产出、验收、证据、未验证项、下一步
   - 长期记忆候选：区分“候选”“已确认”“不应保存”
   - 需要放入收件箱的想法
   - 一到三个下一步
3. 只有以下情况才写入其他区域：
   - 明确的新任务或状态变化 -> `now/` 或对应项目；
   - 用户明确说“记住这个”且内容稳定 -> `self/`；
   - 尚未成形的想法 -> `inbox/`；
   - 仅仅是当日感受 -> 留在日记和总结。
4. 在总结中列出实际更新的文件和未更新的候选，保持可追踪。
5. 原始文件末尾追加归档标记：总结文件路径、归档日期；只追加，不改写原文。

## 事实边界

- 不补写用户没有说过的经历、进度、情绪原因、健康结论或完成状态。
- “做过”“想做”“决定做”“可能做”必须分开。
- 没有证据的项目进展写“未验证”或“用户自述，未核对”。
- 总结不是心理诊断；涉及身体或健康问题时，记录体验并提示需要专业意见，不自行下结论。
- 删除或永久丢弃日记前必须得到用户明确要求；默认只归档，不删除。

## 总结文件格式

使用 [`references/summary-template.md`](references/summary-template.md)。完成后按以下格式向用户简短汇报：

```text
Task:
Result:
Verification:
Uncovered:
Next step:
```
